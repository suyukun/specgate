## 硬规则

三条绝不弯曲的规则。门槛稿的 B4 自检在每次 L 批派发前重复它们——重复才守得住。

1. **最小实现。** 只做当前规格要求的事。不做投机性抽象、配置、容错。50 行能解决就交付 50 行。判据：「高级工程师会说这过度设计吗？」会，就简化。
2. **精准改动。** 只改任务要求你改的行。每一行改动都要能追溯到某个任务或某条验收判据。发现无关死代码？提出来，不删（除非被要求）。只清理自己的改动产生的孤儿（无用 import、变量、函数）。跟随所在文件的既有风格。
3. **先问再动。** 删除文件或数据、改数据库 schema、改公共 API、加依赖、对外发布——每一项都要 {{OWNER}} 明确点头之后才能做。

### 边界——三档

- ✅ **总是**：先理解并复现，再动手；改完跑相关检查并如实报告结果。
- ⚠️ **先问**：硬规则 3 列的一切。
- 🚫 **绝不**：提交密钥或凭据；直接推 main 分支；注释掉报错糊弄编译；编造验证结果。

### 安全要求

- 密钥、token、密码绝不进代码或文档——只走环境变量或密钥管理服务。
- 校验所有用户输入。SQL 参数化。HTML 输出转义。错误信息不得泄漏敏感数据。
- 发现安全问题？立即停下、报告 {{OWNER}}，拍板后才继续。

## 阶段 S0–S3

每条规则都有成本。S0 上一条完整 CI 流水线是纯负担；S3 上它是你的睡眠。阶段声明为当下挑对过程量——它同时救你于「毫无过程」和「过程表演」。

### 各阶段含义

- **S0——先跑通。** 核心想法端到端能跑一次。给核心不变量做冒烟；核心算法测试即规格。无独立审查。无 CI（仅本地 lint 和类型检查）。
- **S1——先做对。** 主流程端到端全绿，带关键路径测试。高风险变更（架构、数据模型、写回回路、权限）落地时即时独立审查。可选极简 CI。
- **S2——扛住真实使用。** 单元与集成回归。覆盖率对核心模块核算。发布候选前整合审查。CI 跑回归套件。
- **S3——能发布。** 全量回归、覆盖率门槛、发布前独立终审。全量 CI＋发布门禁。

哲学：先跑通，再做对，再求快。三条比例律：测试密度跟代码稳定度走；审查频率跟变更风险走；CI 强度跟项目成熟度走。

### 硬信号——全部满足才算处于该阶段

| 阶段 | 信号 |
| --- | --- |
| S0 | 仓库可构建；有一副能跑的骨架或实验；还没有端到端主流程。 |
| S1 | 一条命令端到端跑通主流程（数据 → 处理 → 结果）；关键路径测试全绿；用到真实数据。 |
| S2 | 有真实用户或真实场景产生反馈；需求在迭代；存在发布候选。 |
| S3 | 公开发布；有外部用户；承诺了兼容性。 |

看信号，不看感觉，也不看日历百分比。

### 阶段迁移是显式事件

信号齐 → 有人提议迁移 → {{OWNER}} 拍板 → 更新本文件标题下的 `stage` 标记。那一行是阶段唯一的存放处。

### 防倒退

每个阶段末或里程碑时复查信号。主流程断了，就退回上一阶段的规则。阶段只进不退——除非有意识地推倒重做回原型。

### 技术债台账

S0 欠下的捷径（缺测试、没 CI、跳过的规范）随发生随记进 `docs/tech-debt.md`，在下一次阶段迁移时偿还。这条防止项目永远停在 S0。

### 审查规则——全阶段通用

1. 风险导向：高影响变更落地即审，不「攒到阶段末」。
2. 发布门禁：任何对外发布或定稿，先过一次独立审查。
3. 审查对象是风险变更 diff 与里程碑收口——不是全量代码反复过堂。

### CI 时机

探索期不上 CI。主流程稳定后上轻 CI（lint＋关键路径测试）。全量回归 CI 留到发布期。

### 测试纪律

测试失败修实现，不修测试——除非测试本身错了。绝不为凑覆盖率写形式化测试。

## 开工门槛（门槛稿）

每批活一份门槛稿，从 `docs/plans/gate-doc.template.md` 复制，在任何编码派发之前填好。为什么：四种昂贵的失败——做错东西、多做东西、结果没人能验证、越修越糟的返工循环——全都始于规格，也全都在门槛稿里被最便宜地拦下。

- S/M/L 分级、决策卡、七步收口、止损、验收判据规则书，全部住在门槛稿模板里。那份文件是唯一权威；本节只把本项目绑定到它。
- 开工门禁：门槛稿里存在任何未决（`NC-OPEN`）决策卡时，不从它派发任何编码工作。
- 收口：一批活只有门槛稿过完七步收口才算交付。没收尾的事回填进任务表——没有「口头宣布完成」。
- 返工止损：同一任务失败两轮即停止打补丁。修规格，再重新派发。禁止第三轮盲修。
- 验收模式：S 与 M 批可用「脚本化演示＋结果存档」，{{OWNER}} 事后抽验；L 批与一切给外人看的产出，负责人亲自走一遍。
- 机检：`specgate check` 断言卡片状态、验收判据形态、新门槛稿的 ADR 引用。把它接进 pre-commit 或 CI 之前先问 {{OWNER}}。

## 三层门禁

脚本便宜且不知疲倦，但只会机械匹配；审查能看懂语义但耗注意力；有些判断只有人能做。每层只做自己擅长的事。

1. **硬门禁——确定性、可阻断。** 由 `specgate check` 跑的断言：阶段标记与已装文档、派发前未决卡为零、验收判据形态、收口与新代码提交的 ADR 引用、看板健康。输出 PASS / WARN / FAIL。接入 pre-commit 或 CI 须先问 {{OWNER}}。
2. **软门禁——语义性、建议性。** 对规格与 diff 的一轮审查，报告六类发现：重复、歧义、欠指定、与项目规则冲突、覆盖缺口、跨文档矛盾。只报告，从不阻断。
3. **人管门禁。** {{OWNER}} 圈定批次范围、裁决决策卡、验收演示。solo 模式：三个都是你。

## 任务看板——S1 起

所有没做完的事只有一个家。待办散落在聊天里，迟早变成惊吓。

- `backlog/` 下的看板是待办工作的唯一登记处。发现、需求、决策一律上板成卡——只登记，不顺手修。范围在每批活的开工时圈定。
- 一张卡就是一份任务级规格：标题（动宾一句话）/ 类型 / 优先级 / 描述（现象与出处）/ 入批前补齐的验收判据。
- **单一写者规则**：一张卡同一时刻只归一个工人；派发单写明卡号。状态变更走看板 CLI，绝不手改文件。
- 紧急热修：先修，随即补登卡片。
- 工具：`backlog.md` npm 包（锁 1.55.3）CLI 模式。可选——安静的项目用一份纯 `docs/BACKLOG.md` 也行。接入笔记与已知坑：附录二。
- S1 起的机检门禁：看板自身的健康检查通过，且本文件保有「任务看板」一节。

## 决策日志（ADR）——S0 起

三个月后有人问「当初为什么这么做」，答案不该靠猜。

### 命中任一情形当场记录——不等收尾

1. 方向、架构或数据模型。
2. 流程或团队规则。
3. 技术选型或新依赖。
4. 公共接口或事实源变更。
5. 推翻或覆盖既有决策。

不记录：讨论过但从没拍板的想法，以及 {{OWNER}} 明确说不进 ADR 的事——后者在索引里留一行说明。

### 位置与写法

- 文件：`docs/adr/NNNN-<slug>.md`——四位编号，项目内唯一。索引：`docs/adr/README.md`。会话开场先读最新交接文档和索引里最新的三条。
- 五段加状态头：背景 / 备选 / 决定 / 理由 / 后果。一条决策一个文件，写短。
- 状态值——定义一次，处处沿用：`proposed` · `accepted` · `superseded by ADR-NNNN` · `withdrawn`。
- 旧 ADR 从不改写。新决策通过状态行和指针取代旧决策。
- 模板：附录一。

### 登记挂钩——机判校验 v0.2 提供

- 关闭 `#decision` 看板卡须挂 `adr: ADR-NNNN` 引用，或显式 `adr-exempt: <一行理由>` 标记。
- M / L 门槛稿收口须引用一条 ADR，或带同样的豁免标记。
- 代码类提交（`feat` / `fix` / `perf` / `refactor`）信息里带 `ADR-NNNN`，或 `no-adr: <一行理由>`。docs、chore、test 提交豁免。这堵住「热修绕过门槛稿、决策没入账」的口子。

## 设计规格——S2 起

项目有 UI，或两个以上模块共享接口契约时添加。什么算契约？改它会逼你同时改两个模块，它就是——共享类型、API、事件格式。

- UI token 与 schema 的权威源在 `docs/design/DESIGN.md`。周边文字是人读镜像；两者冲突时，以 token 为准。
- 这个决定归哪个抽屉？两个问题：(a) 绑定具体 UI 或接口契约？→ 设计规格。(b) 关于模块划分、数据流、部署、演进？→ 架构文档。都沾边 → 记一条 ADR 裁决唯一归属，另一处放指针。
- 同一变更同一提交：改权威源的提交同时改设计规格与对应检查。
- 设计规格必须被某份门槛稿的任务表或收口引用。没人引用的设计稿是死重。确定无 UI？在阶段标记旁标 `<!-- design: exempt -->`。

## 架构文档——S1 起

`docs/architecture/` 下两份文档：

- **现状** —— 系统现在是怎么接线的。任何改变了模块、入口或数据流的批次，在同一提交里更新它（收口第 7 步）。可以先作为本文件的「架构现状」一节存在，S2 再拆成独立目录。
- **蓝图** —— 正在长向的目标态。方向变更须记 ADR。

## Git 工作流

- 提交信息用英文、conventional 风格：`feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `perf` / `ci`。
- 一次提交一个逻辑变更。提交前核对暂存区——多个 agent 共用一个仓库时，这防的是误收。

## 验收与交付

- 交付 = 能跑的真实产物 + 真实输出。被阻断？如实说明并给替代方案。绝不编造结果。
- 按阶段定验收量：S0——核心不变量全绿加 lint 与类型检查；全量测试与构建在阶段末或里程碑收口跑。S1 起——测试、lint、构建全绿，才叫完成。

## 附录一 —— ADR 模板

## 附录三 —— 实战沉淀（可持续追加；每条两行以内）

- 探索期跑全量测试是纯负担。全量跑属于阶段末收口。
- 写下来的规则会衰减。没有机检的规则会悄悄死掉——重要就给它配断言。
- 长命令必须显式设超时。默认超时会把分钟级命令截断成重试循环。
- agent 并发会撞限额。同时跑的数量要封顶、退避要长、优先用已有套餐内的模型。
- 阶段迁移看硬信号——一条命令、真实用户、一次发布——从不看感觉。

## 附录四 —— 多 agent 并行（可选；用不上就跳过）

同时派发多个 agent 之后才有用。在那之前忽略本附录。

- **成本阶梯。** 优先用已付费套餐内的模型；自费 API 只作兜底。被限流时：压并发 → 退避等待 → 套餐内换模型 → 最后才是付费 provider。
- **墙钟上限。** 单次超长调用会被掐死且结果不可恢复。把重评审、走查拆成每段约五分钟以内的串行调用，输入裁薄。超时后拆得更小再重跑一次——绝不原样重试同一个超大调用。
- **派发预算。** 按任务类型给软步数预算（页面 150 / 视觉 60 / 修复 80 / 调研 100）。超 100% 就从已有产出中收敛；超 150% 强制止损。预算保的是墙钟和主会话的上下文寿命。
- **契约速查。** 派发单带 5–10 行跨文件接口签名，而不是「把文件都读一遍」。
- **视觉任务。** 图像类活派给有实证视觉能力的模型，且独立成短会话——图在长历史里会被反复重发，越来越贵。同一视觉问题两轮未愈，换 DOM 测量探针量化诊断：截图诊断不了 DOM 结构。几何与对比度走机检；纯审美由人终审。
