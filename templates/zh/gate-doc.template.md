### 文档状态 —— 本文件仅有的状态字段

```markdown
> Status: draft

phase: sizing
```

- 允许的 `Status` 值，仅在此定义：`draft` → `converged` → `archived`。工作进行中 `Status` 保持 `draft`。七步收口全过，改为 `converged`。更新的门槛稿版本取代本稿时，改为 `archived`。
- 允许的 `phase` 值，仅在此定义：`sizing` → `drafting` → `ready` → `converging`。它们记录你所在的位置：定级中、填表中、卡片已清基线已录已派发、收口进行中。
- 这两行原位更新；不要在别处新增状态字段。决策卡状态只活在下面的决策台账里。

### 术语表

| 术语 | 含义 |
| --- | --- |
| 批次 | 一次派发的工作单位。一批一份门槛稿。 |
| 级别（S/M/L） | 第 0 步选的体量档。它决定本表要填多少。 |

| 验收判据（AC） | 编号、可测的 EARS 陈述——「当<条件>时，系统必须<可观察行为>」。规则书在 A 节。 |

## 开工门禁（一条硬规则，以及它为什么划算）

每张未决决策卡都是规格上的一个洞。朝着洞写码就是浪费一轮——你的或你的 agent 的。所以这套流程在门槛处只有一条硬规则：

**开工门槛稿里还有任何 `NC-OPEN` 决策卡时，不派发任何编码工作。**

派发前，先征得用户同意再运行这个检查（任何文本搜索工具都行；要的是计数）：

`grep -c "NC-OPEN" docs/plans/开工门槛-<批次名>_v1.md` —— 结果必须是 0。

## 第 0 步 —— 给批次定级（选一个，写明选了哪个）

诚实地定级是本套件里最便宜的质量控制。L 被悄悄降成 M，就是没人拍板就砍了范围——所以降级必须写理由。

| 级别 | 什么时候算 | 你要填 |
| --- | --- | --- |
| **S——小** | 一个文件、改动少于 50 行、无新依赖，且验收一句话说得清。 | 一行声明（见下）。其余不填。 |
| **M——中** | 一个模块内的一个功能。 | A、D 两节。 |
| **L——大** | 跨模块、新方向、数据 schema 变更，或任何会出现在演示路径上的活。 | 全部：A、B、C、D。 |

- 本批级别：___
- 若从 L 降级，理由是：___

## 派发之前 —— 三查

一分钟，三个拦截。它们挡住三种最贵的派发错误。

1. **卡片已清。** 决策台账无 `NC-OPEN` 行（检查方式见上）。
2. **基线是真的。** D1 的验收命令在开工*之前*已经跑过一次，输出贴在 D1 里。交付之后才补录的基线什么也证明不了。
3. **活在清单上。** 即将派发的一切都出现在 C1 任务表里。发现缺口？报告 {{OWNER}}，由其拍板后再派。派发之后才冒出来的意外，代价翻倍。

## A. 需求

目标：读完 A，{{OWNER}} 能一句话复述目标——且其中没有含糊字眼。

- [ ] **A1 —— 一句话主张。** 给谁、哪个问题、跑通之后有何不同。
  完成当：{{OWNER}} 一句话复述，无追问。
- [ ] **A2 —— 用户故事。** 至多 5 条，按 P1 / P2 / P3 排序。每条可测、可独立交付。
  完成当：砍掉全部 P2 / P3 后，P1 闭环仍然成立。
- [ ] **A3 —— 验收判据。** 每条故事至少一条编号 AC，EARS 句式。规则书见下。
  完成当：每条 AC 说得出检查它的测试或命令。
- [ ] **A4 —— 边界情形。** 至少 3 个：空输入、失败路径、越权尝试、重复提交，或本功能类似的情形。
  完成当：每个情形都有明确的「系统必须……」答案——不是「到时候看」。
- [ ] **A5 —— 非目标。** 本批明确不做的事，逐条列出。
  完成当：{{OWNER}} 已同意。交付了非目标里的东西，是打回重做的正当理由。

### 怎么写 AC —— 本套件唯一的规则书

AGENTS.md 和各处指引都指向这里；它们不重复这些规则。

1. 每条 AC 编号，用 EARS 句式：
   `AC-1: 当<条件>时，系统必须<可观察行为>。`
2. 每条 AC 写明检查它的测试或命令名。写不出来？说明需求没想清——记一张决策卡，回到 A2/A3。
3. 需求里禁用含糊词：*合理、适当、及时、明显、尽快、尽量、友好、优化、完善、支持、考虑、若干*。确实要用，行尾加 `<!-- ok -->`。（词表本身与引文豁免——它们是数据，不是需求。）
4. 非目标（A5）要显式——沉默不是非目标。
5. C1 每条任务行带覆盖标注：`TASK-101（覆盖 AC-1, AC-3）`。这让覆盖可以被机器检查。

## B. 设计（仅 L；M 可跳过）

目标：只决定「留白就会返工」的部分。不在这里设计整个系统。

- [ ] **B1 —— 技术上下文。** 哪些文件与模块会变、哪些依赖不许动、数据放在哪、怎么测。
  完成当：你能大致预测改动文件清单的样子。
- [ ] **B2 —— 关键决策。** 至多 5 条，各带理由与被否的备选。它们是决策日志（`docs/adr/`）的种子。
  完成当：每条说得出被否选项输在哪里。
- [ ] **B3 —— 接口与数据契约。** schema、API 形状、表定义——写成代码（TypeScript 类型、Pydantic 模型、DDL），不写散文。
  完成当：另一个模块今天就能 import 它。
- [ ] **B4 —— 基线自检。** AGENTS.md 的三条硬规则，派发前诚实勾一遍：
  - [ ] *最小实现*：只建 A 要求的——不搞投机抽象、配置、容错。50 行够就交付 50 行。判据：「高级工程师会说这过度设计吗？」会，就简化。
  - [ ] *精准改动*：只动本批任务要求的行；每行改动可追溯到任务或 AC。范围外的「顺手改进」上板，不进这个 diff。
  - [ ] *先问清单*：删文件或数据、改数据库 schema、改公共 API、加依赖、对外发布——每一项都要 {{OWNER}} 明确点头。
  完成当：三个勾都诚实打过，任何「否」都已变成决策卡。

## C. 计划

目标：agent 只凭任务表就能领走任何一条任务——不需要追问。

- [ ] **C1 —— 任务表。** 按用户故事分组。每条任务列出精确文件路径、自己的完成检查、覆盖标注：`TASK-101（覆盖 AC-1, AC-3）`。
  完成当：派发不需要额外解释。
- [ ] **C2 —— 地基任务在前。** 路由壳、骨架注册表、共享类型——使能者单独成组放最上。
  完成当：每条带「解锁什么」说明。
- [ ] **C3 —— 并行标记。** 可并行的任务带 `[P]`；串行依赖写明。同时在飞的任务至多 4 条——安全默认值，匹配多数 agent 的并发上限，也留得出审查余地。
  完成当：计划装得进这个上限。
- [ ] **C4 —— 时间盒与止损。** 每条任务的预期轮数，并把止损写进每份派发单让工人看见：**同一任务失败两轮即停。先修规格（B 节），再谈第三次尝试。**

## D. 验收

目标：「完成」对任何人可查，不必信任任何人的记忆。

- [ ] **D1 —— 验收命令与基线。** 本批的增量检查：聚焦测试、lint、类型检查。首次运行前先问用户，并在开工前把输出贴在这里。工人只跑这些增量检查——全量测试在阶段末收口跑，那才是它该在的地方。
  - 命令：<列出来>
  - 基线（粘贴）：<输出>
- [ ] **D2 —— 审查 diff，不是听故事。** 收口时，每一行改动都在收口表里对到 A 的条目上。没有 AC 或任务背书的改动行属范围外，退回。
- [ ] **D3 —— 演示路径。** 一段 {{OWNER}} 约五分钟能走完的脚本：在哪点、跑哪条命令、看什么、应显示什么。两种模式——按级别选并写明：
  - **with-owner**（L 批与一切给外人看的默认）：{{OWNER}} 亲自走。
  - **scripted**（S、M 与 solo 的默认）：录制一次运行——步骤、命令、预期输出——存档即结果。{{OWNER}} 事后抽验。
  演示步骤：<写在这里>
- [ ] **D4 —— 一句话完成定义。** 本批「绿」意味着什么。必须逐条对上 A3，交付时不得发明新标准。

## 决策卡（needs-clarification 协议）

填 A–D 的过程中你一定会撞上独自答不了的问题。别把猜的答案写进规格——猜出来的答案就是明天的返工。记一张决策卡。

决策卡是下面台账里的一行，with-owner 模式下另给 {{OWNER}} 一条短消息：

```text
卡 1. 录入表单用哪种货币格式？
  a) 一个纯金额；货币在设置里选一次
  b) 每笔都带货币代码
  recommend: a
```

### 两种模式

| | with-owner 模式 | solo 模式 |
| --- | --- | --- |
| 谁来答 | {{OWNER}} | 你自己，把答案写进台账 |
| 卡的形状 | 编号问题（至多两行）、a/b/c 选项、一条推荐 | 同左 |
| 答案怎么落地 | 回复「1a 2b 3 default」——或一次说「default」，整批接受推荐 | 推荐默认直接生效；只在真不同意处推翻 |
| 保护机制 | 读者看不懂的问题责任在 agent——重写问题，绝不让 {{OWNER}} 猜 | 同一标准自测：你自己都说不明白这个问题，就是规格还没 ready |

### 预算与节奏 —— 两种模式通用

- 每批至多 10 张卡，其中至多 4 张阻断性。超预算说明规格本身弱：回去重写，而不是把问题往外推。
- 卡片一批一送，绝不一张一张挤牙膏。
- 紧急例外：热修可以先动手。卡片与理由事后补登。

### 决策台账 —— 卡片状态唯一存放处

卡片状态，定义一次，处处沿用：

- `NC-OPEN` —— 尚无答案。
- `NC-RESOLVED: <决定>` —— 已拍板，决定写在行内。
- `NC-N/A` —— 问题作废（问错了，或移出范围）。

## 收口 —— 七步

七步全过，一批才算交付。之前不算。（「收口」借鉴自 spec-kit：规格与现实相互逼近，直到一致。）

1. **基线绿。** D1 的命令全过，与录入的基线比对。无回归。
2. **diff 对齐。** 每行改动对上 A 表某一条——填下面的表。无范围外编辑。没收尾完的，作为新任务回填进 C1：回填，不是口头「完成」。
3. **演示走通。** D3 演示路径按所选模式走完，{{OWNER}}（或存档录像）确认它展示了该展示的。
4. **卡片全清。** 每张决策卡都是 `NC-RESOLVED: ...` 或 `NC-N/A`。
5. **状态与提交。** 上方 `Status` 改为 `converged`。交付提交信息引用本文件路径。
6. **交接行。** 同一提交里，给项目最新交接文档（`handoffs/` 下）追加一行关于本批的记录。长会话会忘；文件不会。
7. **架构现状。** 本批新增或改变了模块、入口、数据流吗？同一提交里更新架构现状文档。没改——跳过。

## 运行时条款（派发开始之后）

- 返工第 2 轮起：开一个全新会话，只带这份门槛稿和失败清单。返工循环会磨损上下文——拖得越久越糟。
- 止损：同一任务失败两次即停止打补丁。修规格（通常是 B 节），再派。禁止第三轮盲修。
